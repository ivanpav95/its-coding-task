## Template smells to address

**Layering & SOLID (Task 1)**

- Controllers do data access, auditing, premium calculation and ID generation. ✅ Controllers now only map HTTP; the work is in `CoverService`/`ClaimService` (step 3). The premium formula moved unchanged and leaves for `Domain` in Task 5.
- `ClaimsContext` is defined inside `ClaimsController.cs`. ✅ moved to `Infrastructure/Persistence` (step 1).
- `new Auditer(auditContext)` in constructors: no DI, can't be mocked. ✅ `IAuditer` registered in DI (step 5).
- Entities used as API contracts: a client can send `Id` or `Premium` (needs request/response DTOs). ✅ `Application/Contracts` request/response records (step 4).
- Nullable warnings on non-nullable `string` properties. ✅ gone: `required`/`init` on the entities; build has 0 warnings (step 4).

**HTTP behaviour**

- `GET /{id}` for an unknown id returns 204 No Content (ASP.NET Core turns a `null` result into 204) instead of 404. ✅ 404 with ProblemDetails (step 6).
- `DELETE` audits before checking the item exists, and always returns 200. ✅ audit only after a successful delete; 204 or 404 (step 6).
- `GET /Covers/{id}` loads all covers into memory, then filters. ✅ `CoverRepository.GetByIdAsync` filters in Mongo (step 2).
- `POST /Claims` doesn't check that the cover exists. ✅ 400 when the cover doesn't exist (D13, step 6).
- `ComputePremiumAsync` is `async` without `await` (✅ now a plain synchronous action, step 3); a POST that takes query parameters (✅ GET since step 6, D9).
- Deleting a cover leaves its claims pointing at a cover that no longer exists (see D8). ✅ 409 while it has claims (step 6).

**Infrastructure**

- `Program.cs` creates a new `MongoClient` inside the `AddDbContext` lambda, so once per `ClaimsContext` (per request). `MongoClient` holds the connection pool and should be a singleton. ✅ fixed: registered once as `IMongoClient`.
- `ClaimsContext.Claims` is private with helper methods, `Covers` is public: two styles for the same thing. ✅ `ClaimsContext` is now a plain `DbContext` with two public sets; queries live in the repositories (step 2).
- Template leftovers (harmless): `1stMigration.Designer.cs` only describes `ClaimAudit` although `Up()` creates both tables. `Claims.sln` listed a `README.md` at the root while it lived in `docs/` (✅ a root `README.md` exists now).

**Auditing (Task 3)**

- Synchronous `SaveChanges()` inside the request blocks the HTTP pipeline. ✅ queued, saved by a background worker (D4).
- `DateTime.Now` instead of UTC. ✅ UTC from `TimeProvider`, taken when the request happens.

**Data**

- `Cover.Type` is stored as BSON field `"claimType"`; renaming it would break existing documents.

**Testing (Task 4)**

- The only test is an integration test that silently needs Docker (via `Program.cs`). ✅ Split into `Claims.UnitTests` (no Docker) and `Claims.IntegrationTests` (D15, Task 4a).

**Premium (Task 5)**

- P1: the `if`s don't exclude each other, so one day is added up to 3 times (days 0–29: three times, days 30–179: twice). Should be one rate per day, by band. ✅
- P2: the loop stops at `i < 365`, so a 366th day (leap year, allowed by D5.2) would be free. ✅
- P3: day count uses `(end - start).TotalDays` (a double, end exclusive, includes time of day); must follow D5.1 (calendar dates, end inclusive). ✅
- Readability: `if` chain for the type multiplier, magic numbers, loop over days instead of computing each band. ✅ `Domain/PremiumCalculator`: one rate table, per-band arithmetic (Task 5).
- Yacht, end date exclusive as in the template: 10 days → template 39,462.50, correct 13,750.00; 100 days → 298,375.00 vs 132,687.50; 200 days → 529,375.00 vs 262,487.50. The 39,462.50 was confirmed against the running `compute` endpoint.
- No rounding needed: every day rate has at most 2 decimals (Yacht 1375 / 1306.25 / 1265; PassengerShip 1500 / 1470 / 1455; Tanker 1875 / 1837.50 / 1818.75; others 1625 / 1592.50 / 1576.25), so totals are exact in `decimal`.
